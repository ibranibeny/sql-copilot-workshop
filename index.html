Overview

GitHub Copilot, grounded in SQL evidence

Large-language-model assistants are fast at proposing T-SQL and explaining plans, but they can be confidently wrong. This workshop pairs Copilot with two sources of ground truth: Query Store — SQL Server's built-in "flight data recorder" of plans, runtime statistics, and wait statistics — and the Microsoft SQL MCP server, which exposes only bounded, read-only evidence tools. The discipline is simple and repeatable:

TARGET / HYPOTHESIS → MEASURED → DECISION

Propose

Copilot

Explains the procedure, forms hypotheses, and drafts a contract-preserving candidate rewrite.

Measure

Query Store + SQL MCP

Bounded, read-only tools return plans, top queries, waits, memory grants, and A/B run comparisons.

Decide

The DBA

Proves result equivalence, runs frozen A/B trials, and decides what ships. The human owns the outcome.

GitHub Copilot in SSMS

Chat, Agent mode, skills, and MCP

SQL Server Management Studio 22 ships GitHub Copilot as a first-class client, so the same evidence discipline applies whether you drive Copilot from VS Code or from SSMS. The surfaces you use in this lab:

Ask

Chat & inline chat

Natural-language questions about the connected database and T-SQL help, scoped by the active query editor and its connection — not the whole server.

Assist

Slash commands

/explain, /fix, /optimize, and /doc explain, repair, optimize, or document the selected T-SQL. The lab uses /explain and /optimize on the baseline.

Author

Completions & Next Edit

Inline code completions (SSMS 22.2+) plus Next Edit Suggestions that anticipate your next change from recent edits.

Ground

Database instructions

A CONSTITUTION.md stored with the database supplies business rules and an optional least-privilege execution identity for Copilot-generated queries.

Automate

Agent mode & skills (22.7+)

Agent mode pursues a goal autonomously — executing queries, reading plans, and (only with approval) changing schema. Agent skills are reusable, task-specific instruction files. In this lab the reader principal holds no DDL grant, so Agent mode stays read-only here.

Extend

MCP servers

Agent mode is a Model Context Protocol client. Each MCP tool is disabled by default and enabled explicitly; every query or tool call requests confirmation. Ask mode does not support MCP.

Least privilege is the real boundary. Copilot's read-only classification blocks writes, but Microsoft is explicit that it is not a security boundary. Access control is enforced in the database with SELECT/EXECUTE grants; Azure RBAC governs Azure resources, not data.

The Microsoft SQL MCP server

Bounded, read-only evidence — not a query console

The workshop hosts Microsoft's SQL MCP server with Data API Builder 2.0.9 over local stdio. VS Code launches the DAB child process and exchanges JSON-RPC messages (initialize → notifications/initialized → tools/list → tools/call). It exposes exactly 10 tools — never arbitrary SQL, DDL, or server configuration.

4 generic tools

Describe & read

describe_entities, read_records, aggregate_records, execute_entity. Create, update, and delete are disabled.

6 diagnostic tools

Query Store evidence

get_query_store_top_queries, get_query_store_waits, get_procedure_plan_summary, get_memory_snapshot, get_active_workshop_grants, compare_workshop_runs.

Background story

A month-end procedure that eats the memory grant

Adventure Works closes its books every month with a single stored procedure that aggregates sales into a territory-by-customer summary. As the fact table grew past 8 million rows, that month-end run began to dominate an isolated SQL Server query-workspace memory pool: wide rows are materialized early, carried through intermediate work, and aggregated late — so a large share of the pool's grant is consumed on every execution while the business result never changes.

A skeptical DBA is asked to make it faster without changing a single output row. Rather than guess, they pair Copilot's explanations and candidate rewrites with the SQL MCP tools and Query Store measurements, prove equivalence, and decide. Every artifact runs inside a disposable, isolated two-VM lab so the experiment can never touch production.

Architecture

A two-tier, private-by-default lab

Only the Windows 11 administration VM has public ingress — RDP restricted to one facilitator /32. The SQL Server 2022 VM has no public IP; both subnets reach the internet only through a NAT gateway.

Deployment

Gated, evidence-driven provisioning

Deployment uses native Az PowerShell entry points and never bypasses the preflight gate. The flow is deliberate: a read-only preflight, a plan card read aloud, a phrase-gated deployment, then a phase-by-phase readback.

1 · Preflight→ 2 · Plan card→ 3 · Gated deploy→ 4 · Read every phase back

The non-optimized workload you tune

Deployment provisions AdventureWorks2022 with an 8,000,000-row lab.FactSales table and the deliberately non-optimized lab.usp_MonthEndSalesBaseline. You never edit it in place — you build a contract-equivalent candidate, prove equivalence, then compare with frozen A/B trials. The baseline concentrates classic anti-patterns:

Anti-patternWhy it is slow
Non-SARGable date filterA function wraps the column, so no index seek is possible — the 8M-row clustered index is scanned every run.
Wide over-materializationA char(400) payload is carried through intermediate work before aggregating, inflating the query-workspace memory grant.
SELECT * + unindexed sortUnused wide columns are dragged through a sort that can spill to TempDB.
Leading-wildcard LIKELIKE '%…%' on a wide column forces a full scan — no index can seek it.
 
-- Non-optimized: a function on the column defeats an index seek and forces a full scan
SELECT fs.TerritoryID, SUM(fs.SalesAmount) AS TotalSales, COUNT_BIG(*) AS OrderCount
FROM lab.FactSales AS fs
WHERE YEAR(fs.OrderDate) = 2013 AND MONTH(fs.OrderDate) = 6
GROUP BY fs.TerritoryID;

-- Optimized: SARGable half-open range + a covering index (create the index as admin, not via SQL MCP)
SELECT fs.TerritoryID, SUM(fs.SalesAmount) AS TotalSales, COUNT_BIG(*) AS OrderCount
FROM lab.FactSales AS fs
WHERE fs.OrderDate >= '2013-06-01' AND fs.OrderDate < '2013-07-01'
GROUP BY fs.TerritoryID;
-- CREATE NONCLUSTERED INDEX IX_FactSales_OrderDate_Territory
--   ON lab.FactSales (OrderDate, TerritoryID) INCLUDE (SalesAmount);
-- Rollback: DROP INDEX IX_FactSales_OrderDate_Territory ON lab.FactSales;
The goal is to move query-workspace grant utilization from an approximately 80% baseline toward approximately 40% — a target, not a promised result. If the target is missed, report the observed outcome.
